= Documenting Vault-Encrypted Secrets in AgnosticV
:toc:
:toc-placement: preamble

Every vault-encrypted variable in the repository must have a structured comment block immediately above it.
CI enforces this automatically: if you modify a secret file in a PR and the comments are missing or malformed, the check fails.

== Why

When a credential leaks, gets compromised, or simply expires, the team needs to answer fast:

* Who owns this?
* What does it grant access to?
* How bad is it if it leaked?
* How do I rotate it?
* Where is the decrypted value exposed at runtime?

Without structured documentation, answering these questions means reverse-engineering variable names and grepping `#include` references across hundreds of catalog items.

== Required Fields

Place a `# @field: value` comment block above *each* `!vault` variable. Seven fields are mandatory:

[cols="1,2,3", options="header"]
|===
| Field | Format | Description

| `@owner`
| `Name <email>` (comma-separated for multiple)
| Person(s) or team responsible for this credential.

| `@purpose`
| Free text
| What this credential does.

| `@impact`
| `HIGH`, `MEDIUM`, or `LOW` followed by a dash and explanation
| What happens if this credential leaks.

| `@expiration`
| `YYYY-MM-DD`, `never`, or `UNKNOWN`
| When the credential expires.

| `@rotation`
| Free text
| How to rotate or renew this credential.

| `@source`
| URL or description
| Where the credential was created or can be regenerated.

| `@exposure`
| Free text
| Where the decrypted value ends up at runtime.
|===

=== Impact Levels

* *HIGH* — Can access or destroy production resources, customer data, or external services with broad scope (e.g., cloud admin keys, org-level OAuth tokens).
* *MEDIUM* — Can access dev/staging environments or internal-only systems with limited blast radius (e.g., dev cluster tokens, internal API keys).
* *LOW* — Limited scope, easily revokable, no customer data exposure (e.g., test-only credentials, time-limited workshop tokens).

=== The UNKNOWN Placeholder

Any field can be set to `UNKNOWN` (case-insensitive) when you genuinely don't know the answer — for example, when you're modifying a secret file you didn't create. This is better than guessing: it satisfies CI while flagging the field for future investigation.

== Template

Copy this block above each vault variable. A full template is also available at `includes/secrets/TEMPLATE.yaml`.

[source,yaml]
----
# @owner: Your Name <your.email@redhat.com>
# @purpose: What this credential does (one line)
# @impact: HIGH|MEDIUM|LOW - what happens if this credential leaks
# @expiration: YYYY-MM-DD or "never"
# @rotation: How to rotate or renew this credential
# @source: URL or description of where this credential was created
# @exposure: Where the decrypted value ends up at runtime
----

== Examples

=== Single-Variable File

[source,yaml]
----
---
# @owner: Guillaume Core <gucore@redhat.com>
# @purpose: OAuth token for Quay.io org-admin API access
# @impact: HIGH - leaked token grants full org admin on quay.io/rhpds
# @expiration: 2027-01-15
# @rotation: Regenerate in quay.io org settings > Applications > rhpds-sandbox
# @source: https://quay.io/organization/rhpds?tab=applications
# @exposure: AgnosticD execution only, not persisted
quay_io_oauth_token: !vault |
  $ANSIBLE_VAULT;1.2;AES256;gpte-vault-0
  ...
----

=== Multi-Variable File

Each variable gets its own block. Fields don't carry over from one variable to the next.

[source,yaml]
----
---
# @owner: Guillaume Core <gucore@redhat.com>
# @purpose: AWS access key ID for ROSA provisioning (identifier only)
# @impact: LOW - read-only identifier, useless without the secret key
# @expiration: never
# @rotation: Regenerate in AWS IAM > Users > rosa-provisioner > Security credentials
# @source: https://console.aws.amazon.com/iam/home#/users/rosa-provisioner
# @exposure: injected as env vars during AgnosticD execution
rosa_aws_access_key_id: !vault |
  $ANSIBLE_VAULT;1.2;AES256;gpte-vault-0
  ...

# @owner: Guillaume Core <gucore@redhat.com>
# @purpose: AWS secret access key for ROSA provisioning
# @impact: HIGH - combined with the access key, grants full programmatic access
# @expiration: never
# @rotation: Regenerate in AWS IAM > Users > rosa-provisioner > Security credentials
# @source: https://console.aws.amazon.com/iam/home#/users/rosa-provisioner
# @exposure: injected as env vars during AgnosticD execution
rosa_aws_secret_access_key: !vault |
  $ANSIBLE_VAULT;1.2;AES256;gpte-vault-0
  ...
----

=== Using UNKNOWN

When you inherit a secret you can't fully document:

[source,yaml]
----
---
# @owner: Alice <alice@example.com>
# @purpose: Some token inherited from previous team
# @impact: UNKNOWN
# @expiration: UNKNOWN
# @rotation: UNKNOWN
# @source: UNKNOWN
# @exposure: UNKNOWN
inherited_token: !vault |
  $ANSIBLE_VAULT;1.2;AES256;gpte-vault-0
  ...
----

== Rules

* The `# @field:` block goes immediately above the `!vault` variable it documents.
* A blank line between the last `@` comment and the variable is allowed.
* A non-vault YAML key between the comments and the vault variable *resets* the block — the comments won't carry over.
* Regular `#` comments (without `@`) can be mixed in without breaking anything.
* Field order is not enforced. Recommended order: owner, purpose, impact, expiration, rotation, source, exposure.
* Each field is a single line — multi-line values are not supported.

== CI Enforcement

The check runs automatically on every PR as part of the existing `all-checks-pr.yml` GitHub Actions workflow.

=== What Gets Checked

Any YAML file modified in the PR is scanned for `!vault` variables. If a file contains vault variables, each one must have the required `@` comment block. Files not touched in the PR are not checked.

=== What the Check Validates

. Every `!vault` variable in the changed files has all 7 required `@` fields.
. `@impact` starts with `HIGH`, `MEDIUM`, `LOW`, or is `UNKNOWN`.
. `@expiration` is a valid `YYYY-MM-DD` date, `never`, or `UNKNOWN`.

=== What Happens on Failure

The CI posts a comment on the PR listing every undocumented variable and what's missing:

----
🔒 Secret documentation errors:

ERROR: includes/secrets/rosa-aws.yaml
  rosa_aws_access_key_id (line 3): missing: @impact, @expiration, @rotation
  rosa_aws_secret_access_key (line 11): missing: @owner, @purpose, @impact, @expiration, @rotation, @source, @exposure

2 undocumented vault variable(s) found.

Required fields: @owner, @purpose, @impact, @expiration, @rotation, @source, @exposure
See includes/secrets/TEMPLATE.yaml for the required format.
----

=== How to Fix

Add the required `@` comments above each flagged variable. Use `includes/secrets/TEMPLATE.yaml` as a starting point. Use `UNKNOWN` for fields you can't answer.

== FAQ

*Do I have to document every secret in the repo?*

No. Only vault variables in YAML files you modify in your PR. Existing undocumented secrets are grandfathered until the file is touched.

*Can I use `UNKNOWN` for everything?*

Yes, but please fill in what you can — at minimum `@owner` (you) and `@purpose`. The goal is to build up documentation over time.

*What if a file has both vaulted and non-vaulted variables?*

Only `!vault` variables require the `@` comment block. Plain variables are ignored by the checker.

*Who should be listed as `@owner`?*

The person or team who manages the credential — whoever would rotate it if it leaked. Not necessarily the person adding the `#include`.

*What counts as `@exposure`?*

Where the decrypted value ends up at runtime. Examples: "AgnosticD execution only, not persisted", "written to ~/.config/creds on target host", "stored in OpenShift Secret in user namespace", "injected as env var in workshop pods".
