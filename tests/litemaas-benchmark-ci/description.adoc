[NOTE]
====
*What does "LLM Queries per Learner" mean?*

This is how many times each learner will ask the LLM a question during the workshop.

*Example 1: Traditional Workshop (using CLI, notebooks, etc.)*

In a 90-minute workshop, a learner might:
• Ask the LLM to explain a concept (1 query)
• Request code generation (2 queries)
• Debug an error (3 queries)
• Ask follow-up questions (4 queries)
• Complete lab exercises using LLM (5-10 queries total)

*Example 2: LibreChat/MCP Workshop (with tool calling)*

LibreChat + MCP users have ongoing conversations AND tool calls:
• Initial question + 5-10 follow-ups per topic (1 conversation thread)
• Multiple conversation threads during workshop (2-3 threads)
• **Each message = 1 query**
• **Each tool call = 1-3 additional queries** (tool decision + result processing)

For 90-min LibreChat/MCP workshop:
• **Light usage (minimal tools)**: 15-20 queries
  - 10 user messages + 5-10 tool calls
• **Moderate usage (regular tools)**: 30-40 queries
  - 15 user messages + 15-25 tool calls
• **Heavy usage (tool-heavy workflow)**: 50+ queries
  - 20 user messages + 30+ tool calls (chained tool use)

**Important for MCP:** Tool calling **doubles or triples** query count compared to plain chat.

Set this to match your workshop's tool usage intensity.
====

TIP: When ordering, enter the **expected number of learners** (not technical P50/P95 values). For multiple sessions in a day, test with the per-session count (e.g., 60 users) - if one session passes, all will pass.

== Overview

Self-service performance testing and capacity validation for LiteMaaS deployments. Run multi-turn conversation benchmarks to validate TTFT (Time to First Token) performance, prefix caching effectiveness, and load capacity.

== What You Get

* **Dedicated SNO Cluster**: OpenShift 4.20 Single Node cluster from CNV pool
* **Performance Metrics**: TTFT P50/P95/P99, mean latency, throughput
* **Cache Validation**: Prefix caching speedup ratio and effectiveness
* **Model Selection**: Benchmark any available LiteMaaS model
* **Load Testing**: Configurable concurrent conversations and turns
* **Automatic Results**: Metrics displayed in service info page
* **Auto-cleanup**: Cluster and all resources deleted on destroy

== Configuration Parameters

When ordering this catalog, you can configure these parameters to match your testing needs:

=== Model Selection

Select one or more models to benchmark. At least one model must be selected.

TIP: Start with one model for quick validation, then compare multiple models to find the best fit.

=== Load Configuration

[cols="1,3,1"]
|===
|Parameter |What It Does |Recommended Values

|*Concurrent Conversations*
|Simulates parallel users making requests at the same time. Higher = more stress.
|**Quick test:** 5-10 +
**Workshop validation:** 50-100 +
**Load test:** 100-200

|*Turns per Conversation*
|Number of follow-up questions in each conversation. Tests prefix caching effectiveness.
|**Quick test:** 3-5 +
**Standard:** 10 +
**Deep cache test:** 20-50

|*Parallel Workers*
|How many requests run simultaneously. Higher = more concurrent load.
|**Light:** 2-4 +
**Medium:** 4-8 +
**Heavy:** 8-16

|*Max Tokens*
|Maximum response length. Lower = faster responses.
|**Quick:** 200-300 +
**Standard:** 500 +
**Long form:** 1000-2000
|===

=== Request Timing

[cols="1,3,1"]
|===
|Parameter |What It Does |Recommended Values

|*Min Request Delay*
|Minimum pause between requests (simulates user reading/typing).
|**Stress test:** 0.1-0.5s +
**Realistic:** 0.5-1.0s +
**Natural:** 1.0-2.0s

|*Max Request Delay*
|Maximum pause between requests.
|**Stress test:** 0.5-1.0s +
**Realistic:** 2.0-3.0s +
**Natural:** 3.0-5.0s
|===

TIP: Random delays between min/max simulate realistic user behavior. Lower delays = higher stress on the system.

=== Virtual Key Configuration

[cols="1,3"]
|===
|Parameter |What It Does

|*Key Duration*
|How long your temporary API key remains valid (3d, 7d, 10d, 30d). Choose based on how long you need to access the benchmark results.
|===

== How It Works

1. **Virtual Keys**: Creates temporary LiteMaaS API key for selected models
2. **Seed Documents**: Uses 11 real-world documents (code + text)
3. **Multi-Turn**: First turn = full document, later turns = follow-ups
4. **Parallel**: Multiple workers simulate concurrent users
5. **Metrics**: Parses output for TTFT, speedup, throughput

== Technical Details

=== Benchmark Tool

* Tool: https://github.com/rh-aiservices-bu/multi-turn-benchmarking
* Container: `quay.io/hayesphilip/multi-turn-benchmark:0.0.1`
* Runs as Kubernetes Job on dedicated SNO 4.20 cluster

=== What Gets Tested

* **TTFT (Time to First Token)**: Response latency
* **Prefix Caching**: KV cache effectiveness across conversation turns
* **Throughput**: Requests per second
* **Concurrency**: Multiple parallel users
* **Realistic Load**: Random delays, diverse prompts

=== Cleanup

All resources are automatically removed when you destroy the catalog item:

* Benchmark Job deleted
* Benchmark Pods deleted
* Virtual keys removed
* SNO cluster deleted (complete cleanup)
