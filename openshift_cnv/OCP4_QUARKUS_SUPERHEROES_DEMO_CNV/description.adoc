Use sample applications to demo Quarkus features, patterns, and best practices. Quarkus has excellent https://quarkus.io/guides[documentation^] and https://github.com/quarkusio/quarkus-quickstarts[quickstarts^] to help developers become familiar with various features in the Quarkus ecosystem. However, these guides are missing a fully-implemented sample set of real-world applications that use Quarkus's features, patterns, and best practices, while also reflecting problems Quarkus tries to solve. In addition to being fun, these sample applications must meet the following requirements:

* The overall architecture must be a multi-service microservices architecture.
* The application needs to offer more than "hello world" but less than "kitchen sink," instead showcasing a set of common capabilities, such as:
** https://en.wikipedia.org/wiki/Representational_state_transfer[REST^]
** https://en.wikipedia.org/wiki/WebSocket[WebSockets^]
** Database interaction (SQL and NoSQL)
** GenAI/ChatGPT integration
** Messaging
** https://quarkus.io/guides/smallrye-health[Health checks^]
** https://quarkus.io/guides/micrometer[Observability, monitoring, and metrics^]
** https://quarkus.io/guides/opentelemetry[Integration with OpenTelemetry^] for distributed tracing
** Integration with https://quarkus.io/guides/kafka-schema-registry-avro[Apache Avro^] and schema registries
** https://quarkus.io/guides/openapi-swaggerui[OpenAPI^] integration
** Server-side template rendering with https://quarkus.io/guides/qute[Quarkus Qute^]
** Service discovery and client-side load balancing with http://smallrye.io/smallrye-stork[SmallRye Stork^]
** Microservice https://quarkus.io/guides/smallrye-fault-tolerance[resilience patterns^]
** Common testing scenarios
* Additionally, services must attempt to show different practices, such as:
** Constructor injection vs. field injection of beans within an application
** Reactive/asynchronous and imperative/synchronous/blocking
** Repository pattern vs. active record pattern for data access
* The applications must be kept up-to-date with each Quarkus version, be part of the https://github.com/quarkusio/quarkus-ecosystem-ci[standard Quarkus ecosystem continuous integration^], and be shown on the https://status.quarkus.io/[Quarkus status dashboard^].
* Include both blocking and reactive examples as much as possible.
* The system as a whole must:
** Be simple to build, run, deploy, and demo on a local developer machine or in Kubernetes
** Show how Quarkus can help facilitate local development of independent microservices
** Be contained in a https://github.com/quarkusio/quarkus-super-heroes[single GitHub repository^] for simplicity, but not as a multi-module project where projects depend on one another
* Each application within the system must:
** Provide https://quay.io/quarkus-super-heroes[container images^] for Java version 17, both Java VM and native, on both amd64 and arm64 platforms
** Be fully documented
** Have fully automated and documented CI/CD practices
** Contain a complete test suite of unit and integration tests

Think of it as the "PetClinic" or "Cool Stuff Store" for Quarkus. Based on your use case, you can decide what you want to show for a particular demo. You might want to focus on the UIs, or maybe you're interested in explaining the overall architecture or showcasing failures. Additionally, you can use the demo as the application itself if you want to demo something around the application, like continuous delivery, rolling updates, pipelines, or integration with AMQ Streams/Prometheus, just to name a few. The system is very easy to deploy and demo. Using this system as a baseline for other demos helps spread the word about the Quarkus sample application's existence and showcase Quarkus as the technology of choice when performing demos. This can go a long way in a customer's perception of Quarkus and Red Hat, even if the focus of the demo isn't on Quarkus.
