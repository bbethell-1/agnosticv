Quarkus Superheroes Demo

Quarkus has excellent documentation and quickstarts to help developers become familiar with various features in the Quarkus ecosystem. However, what was missing was a fully-implemented sample set of real-world applications that use these features, patterns, and best practices while also reflecting problems Quarkus is trying to solve.

In addition to simply being fun, some other requirements were essential as well:

  • The overall architecture should be a multi-service microservices architecture.
  • It needs to be more than "hello world" but not the "kitchen sink," picking a set of common capabilities, such as
    • REST
    • WebSockets
    • Database interaction (SQL & NoSQL)
    • Messaging
    • Health checks
    • Observability, monitoring, & metrics
    • Integration with Apache Avro & schema registries
    • OpenAPI integration
    • Server-side template rendering with Quarkus Qute
    • Service discovery & client-side load balancing with SmallRye Stork
    • Microservice resilience patterns
    • Common testing scenarios
  • Additionally, services should attempt to show different practices, such as
    • Constructor injection vs field injection of beans within an application
    • Reactive/asynchronous and imperative/synchronous/blocking
    • Repository pattern vs active record pattern for data access
  • The applications should be kept up-to-date with each Quarkus version and be part of the standard Quarkus ecosystem continuous integration and shown on the Quarkus status dashboard.
  • There should be both blocking and reactive examples as much as possible.
  • The system as a whole should
    • Be simple to build, run, deploy, and demo on a local developer machine or in Kubernetes.
    • Show how Quarkus can help facilitate local development of independent microservices.
    • Be contained in a single GitHub repository for simplicity, but NOT a multi-module project where projects depend on one-another.
  • Each application within the system should
    • Be simple to build, run, deploy, and demo on a local developer machine or in Kubernetes.
    • Provide container images for Java versions 11 and 17, both JVM and native, on both amd64 & arm64 platforms.
    • Be fully documented.
    • Have fully automated and documented CI/CD practices.
    • Contain a complete test suite of unit and integration tests.

Think of it as the "PetClinic" / "Cool Stuff Store" / etc for Quarkus.

You can decide based on your use case what you want to show for a particular demo. Maybe you want to focus on the UIs? Or maybe you're interested in explaining the overall architecture? Maybe you want to showcase failures?

Additionally, the demo can be used as "the application" if you want to demo something around the application, like continuous delivery, rolling updates, pipelines, integration with AMQ Streams/Prometheus, etc, just to name a few.

The system is very easy to deploy and demo. Using this system as a baseline for other demos will help spread the word about the Quarkus sample application's existence as well as help showcase Quarkus as the technology of choice when performing demos.

This can go a long way in a customer's perception of Quarkus and Red Hat, even if the focus of the demo isn't Quarkus.
