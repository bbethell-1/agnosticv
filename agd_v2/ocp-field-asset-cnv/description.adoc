Provides an OpenShift cluster with GitOps already installed. You bring a Helm chart — manifests, Ansible, or both — and OpenShift GitOps deploys it.

[NOTE]
====
The GitOps-controlled deployment is not monitored or verified by the RHDP platform.
You have control (and responsibility) over exactly what is deployed to the cluster.
====

== Instructions

When you order, start with cluster size (SNO or multi-node) and OpenShift version. If you picked multi-node, you can also set worker count, CPU, and memory. The cluster always comes with an authentication provider (RHBK), OpenShift Lightspeed, and OpenShift GitOps.

Next, you can check one or more *base workloads* so those operators are installed before GitOps runs:

* *OpenShift Virtualization* — operator and HyperConverged instance, ready to run VMs
* *OpenShift AI 3* — operator and Data Science Cluster. On this CNV item there is no GPU; use LiteMaaS if you need model access.
* *Ansible Automation Platform* — licensed Automation Controller (Hub, EDA, and AAP Lightspeed are not included)

Leave all three unchecked if you just want vanilla OpenShift and GitOps.

After that, the rest of the form is optional:

* *Create users on cluster?* — extra users besides the admin, with a user count when enabled.
* *Existing GitOps Repo?* — check this to have GitOps deploy your chart. Fill in the GitOps URL, revision, and *GitOps Path*. The path is the entry point: the directory that contains the Helm chart GitOps will start from. For the link:https://github.com/rhpds/field-sourced-content-template.git[Field Sourced Assets^] template that is `examples/helm` or `examples/ansible`. If you are using your own repo, use the equivalent path to your chart.
** `examples/helm` — an App of Apps. Each component lives under `components/` and can be turned on or off.
** `examples/ansible` — an Ansible Runner job that runs the playbook and roles you define.
** Private GitHub repos work. Check that option and provide an access token.
* *Enable LiteMaaS/MaaS API Keys* — for AI/LLM demos. Provisions a temporary key for a selected model (3, 7, 10, or 30 days) and injects `litemaas.*` into your Helm chart.

=== Values passed to your Helm chart

Your chart gets a handful of values so it can talk to the cluster and the bases you selected:

* `deployer.domain` and `deployer.apiUrl`
* `guid` and `user.count`
* `bases.virt`, `bases.rhoai`, and `bases.aap` — booleans for the base workloads you selected
* OpenShift console URL and admin credentials
* Keycloak console URL and admin credentials
* AAP controller URL and admin credentials, when AAP is selected
* OpenShift AI dashboard URL, when AI is selected
* `litemaas.apiUrl`, `litemaas.apiKey`, and `litemaas.model`, when LiteMaaS is enabled

You can gate optional templates on the `bases.*` flags so they only render when that operator is actually on the cluster.

=== How GitOps bootstrap works

The catalog creates an Argo CD Application pointing at your chart. The role that does that is link:https://github.com/rhpds/core_workloads/tree/main/roles/ocp4_workload_field_content[ocp4_workload_field_content^] in the AgnosticD v2 core workloads repository.
